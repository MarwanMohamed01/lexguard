# Gretel PII eval

Measures `@lexguard/guardrails` PII redaction on a public, independent dataset.

- **Dataset:** [gretelai/gretel-pii-masking-en-v1](https://huggingface.co/datasets/gretelai/gretel-pii-masking-en-v1),
  test split (5,000 synthetic documents in 47 domains, 403 of them contract-like).
- **Licence:** Apache-2.0, © Gretel.ai. The data is downloaded locally and never committed;
  only our results (`../results/gretel.json`) are.
- **Pinned revision:** `e06eb1499ca8d54470f085021cd8e54f9efac7fd`, verified by SHA-256 in `fetch.mjs`.

## Run

```bash
npm run fetch:gretel -w @lexguard/evals
npm test -w @lexguard/evals
```

CI downloads the same pinned file (cached by revision) and fails if precision or recall
drops below the thresholds in `report.test.ts`. Locally, the eval is skipped until the data
is downloaded. For a case-by-case view of the 403 contract-like documents:

```bash
npm run eval:watch -w @lexguard/evals
```

## How it is scored

- Only Gretel types we claim to detect are scored: `email` → EMAIL, `phone_number` → PHONE,
  `credit_card_number` → CARD. Gretel contains no IBANs.
- **strict**: exact `(type, value)` match. **overlap**: our redaction covers at least part of
  the labelled value.
- A redaction that hits a labelled entity of another type (e.g. an ID detected as a phone) is
  counted as `redactedOtherPii`, not as a false alarm.
- `coverage` shows how much of all labelled PII falls into types we support at all.
- Card numbers are also reported on the Luhn-valid subset, because many synthetic card
  numbers fail the checksum (and some labels are truncated).

## Results history (strict scores, all 5,000 rows)

| Change                                                                       | Precision | Recall | Phone P / R   |
| ---------------------------------------------------------------------------- | --------- | ------ | ------------- |
| Baseline (`+` or leading-0 phones only)                                      | 0.956     | 0.723  | 0.864 / 0.456 |
| Phone fix: US formats, extensions, no line breaks, 0-numbers need separators | 0.967     | 0.807  | 0.925 / 0.700 |
| Bracketed area codes `(02) 6295 0291`                                        | 0.968     | 0.834  | 0.932 / 0.778 |
| **Generic: libphonenumber VALID, regions US/GB/AU** (current, see D11)       | 0.966     | 0.750  | 0.912 / 0.537 |
| Same, no regions configured (international `+` numbers only)                 | 0.981     | 0.635  | 0.943 / 0.200 |

The first three rows used hand-written US/UK/AU patterns, partly tuned on Gretel's misses, so
they are optimistic for Gretel and would not carry over to other countries. Contract-like
documents only (403), current: precision 0.967, recall 0.781.

### Known remaining misses (deliberate)

- **Cards failing the Luhn checksum or truncated in the label (209 of 216 card misses).**
  Not real card numbers; rejecting them is correct.
- **Phones written as bare digit runs** (`5635402307`, `08081570043`, ~160). Indistinguishable
  from account, customer or company numbers without context; matching them would bring back
  false alarms on contracts. Revisit with context-aware detection (M7).
- **12-digit Maestro cards** (a handful). Allowing 12 digits would add false alarms on IDs.

## Caveats

The data is synthetic (generated by a language model), and labels are not perfect: some
company addresses such as `support@example.com` are not labelled, which shows up as false
alarms.
