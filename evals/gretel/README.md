# Gretel PII eval

Measures `@lexguard/guardrails` PII redaction on a public, independent dataset.

- **Dataset:** [gretelai/gretel-pii-masking-en-v1](https://huggingface.co/datasets/gretelai/gretel-pii-masking-en-v1),
  test split (5,000 synthetic documents in 47 domains, 403 of them contract-like).
- **Licence:** Apache-2.0, © Gretel.ai. The data is downloaded locally and never committed;
  only our results (`../results/gretel.json`) are.
- **Pinned revision:** `e06eb1499ca8d54470f085021cd8e54f9efac7fd`, verified by SHA-256 in `fetch.mjs`.

## Run

```bash
npm run fetch:gretel -w @lexguard/evals
npm test -w @lexguard/evals
```

The eval is skipped when the data is not downloaded (for example in CI).

## How it is scored

- Only Gretel types we claim to detect are scored: `email` → EMAIL, `phone_number` → PHONE,
  `credit_card_number` → CARD. Gretel contains no IBANs.
- **strict**: exact `(type, value)` match. **overlap**: our redaction covers at least part of
  the labelled value.
- A redaction that hits a labelled entity of another type (e.g. an ID detected as a phone) is
  counted as `redactedOtherPii`, not as a false alarm.
- `coverage` shows how much of all labelled PII falls into types we support at all.
- Card numbers are also reported on the Luhn-valid subset, because many synthetic card
  numbers fail the checksum (and some labels are truncated).

## Caveats

The data is synthetic (generated by a language model), and labels are not perfect: some
company addresses such as `support@example.com` are not labelled, which shows up as false
alarms.
